# ADR 0005: Redis 쿠폰 예약과 Stream 기록

- 상태: Accepted (내부 컴포넌트 실험 범위)
- 날짜: 2026-11-24
- 관련: [DB 발급 기준 구현](0004-db-coupon-issuance.md), [검증 보고서](../results/2026-11-24-redis-reservation.md)

## 문제와 범위

현재 공개 API는 MySQL에서 발급을 확정한다. Redis 방식의 첫 단계로 중복·기간·재고 검사와 예약, 발급 작업 기록을 구현한다. 예약 성공은 최종 발급 확정이 아니다. MySQL을 최종 발급 기록의 기준으로 유지한다.

이번 구현은 `modules/event`의 `RedisReservationStore`이며 HTTP에서 호출하지 않는다. 기존 DB 직접 발급과 Redis 예약을 동일 이벤트에 병용하면 서로 다른 재고로 접수하므로 안전하지 않다. 공개 연결에 앞서 이벤트의 발급 방식 선택·전환을 DB에서 관리하고 다른 방식의 쓰기를 차단해야 한다. API에 실험용 예약 엔드포인트를 먼저 노출하지 않는다.

Worker는 Phase 2의 별도 앱으로 도입한다. 이번에는 Worker·Consumer Group·ACK·자동 복구를 구현하지 않는다.

## 키와 작업 계약

| 키 | 타입 | 내용 |
|---|---|---|
| `coupon:reservation:{eventId}:state` | Hash | `total`, `remaining`, `startsAt`, `endsAt`, `user:{userId}` → Stream 메시지 ID |
| `coupon:reservation:{eventId}:stream` | Stream | `schemaVersion=1`, `eventId`, `userId`, `reservedAt` |

실제 키에는 숫자 ID를 넣으며 `{123}`처럼 같은 이벤트의 hash tag를 공유한다. Cluster 사용 시 같은 슬롯에 배치하기 위한 구조이며 실제 Cluster 검증은 별도다. 이벤트별 Stream이므로 후속 Worker에 대상 이벤트 탐색·그룹 생성 절차가 필요하다. 전역 Stream 검색 비용을 숨기거나 Cluster 지원 완료로 설명하지 않는다.

재고와 사용자별 예약 결과를 하나의 Hash에 둬 단일 `HSET` 명령으로 변경한다. 서로 다른 Set·재고 키를 순차 변경하는 것보다 쓰기 단계 수가 적다. 사용자별 기록은 발급 수만큼 증가하며 TTL·Stream 트리밍은 이번 범위에서 사용하지 않는다. 키는 다른 기능의 캐시로 사용하지 않고 Eviction 없이 보존해야 한다.

ID는 Java `long`을 문자열로 전달하며 Lua 숫자로 변환하지 않는다. `Long.MAX_VALUE`도 손실 없이 작업에 저장한다. 수량은 양의 Java `int` 범위다. 시간은 앱 Clock 기준 UTC 1000~9999년의 고정 길이 마이크로초 문자열이며 시작 포함·종료 제외다. 앱 간 시간 오차와 Redis 대기 시간은 여전히 고려해야 한다.

## 초기화와 재요청

`initialize(Event)`는 발급 전 이벤트 스냅샷만 받는다. 초기 총량과 잔량이 같아야 하며 DB 자동 조회·자동 초기화는 없다. 같은 ID·수량·기간의 재초기화는 재고를 채우지 않고 `false`를 반환한다. 다른 설정이나 Stream만 남은 상태는 거절한다.

이 메서드는 실제 DB에 발급 기록이 없는지 또는 스냅샷이 최신인지 보장하지 않는다. 호출자가 독점 준비 구간을 확보해야 한다. 상태와 Stream이 모두 유실됐을 때 과거 처리 여부도 Redis만으로 판단할 수 없으므로, 오래된 스냅샷으로 재초기화하면 안 된다.

같은 이벤트·사용자의 재요청은 새 작업을 만들지 않고 같은 메시지 ID와 `replayed=true`를 반환한다. 중복 확인을 기간·품절 검사보다 먼저 수행하므로 종료 후 재요청도 기존 접수 결과를 받는다. 이 계약은 DB API의 409 `ALREADY_ISSUED`와 다르다. `Reservation`에는 최종 상태 필드를 넣지 않았다. Worker가 없으므로 `CONFIRMED`·`FAILED`를 임의로 반환하지 않는다.

## Lua 실행과 오류 처리

정상 경로는 다음 순서다.

1. 키 타입, 메타데이터, 잔량 범위를 검증한다.
2. `총량 - 잔량 = 사용자 예약 수 = Stream 길이`를 확인한다. 부분 유실·삭제가 감지되면 변경 없이 중단한다. 임의 데이터 변조 전체를 검증하는 방식은 아니다.
3. 기존 사용자 예약이면 같은 결과를 반환한다.
4. 기간·품절·쓰기 및 보상 명령의 ACL 권한을 확인한다.
5. `XADD`로 작업을 기록한다. 실패하면 재고·사용자 기록은 변경하지 않는다.
6. 한 번의 `HSET`으로 잔량과 사용자 예약을 함께 기록한다.
7. `HSET` 오류라면 방금 추가한 메시지를 `XDEL`로 보상 삭제한다. 보상도 실패하면 대조가 필요한 오류를 반환한다.

Lua 실행 중 다른 클라이언트 명령은 끼어들지 않는다. 성공 경로의 결과를 클라이언트가 일부만 관찰하지 않도록 묶은 것이며, Redis Lua에 DB처럼 자동 롤백이 있다는 뜻은 아니다. [Redis Lua 실행 문서](https://redis.io/docs/latest/develop/programmability/eval-intro/)의 실행 원자성과 [Lua API의 오류 처리](https://redis.io/docs/latest/develop/programmability/lua-api/)를 기준으로 한다.

보상 삭제는 오류 처리 코드이며 서버 프로세스 중단·OOM·복제·영속성 유실을 모두 복구하는 트랜잭션이 아니다. 재시작 후 정합성 대조가 필요하며 길이 검사만으로 같은 크기의 잘못된 데이터까지 판별할 수 없다. 네트워크 응답 유실 시에는 초기화·재고 복원 대신 같은 이벤트·사용자로 재요청한다.

## 후속 확정과 순서

후속 Worker는 DB 트랜잭션에서 이미 확정된 발급을 판별하고, 처음 처리할 때만 DB 재고를 조건부 차감하며 발급 기록을 저장한다. DB 커밋 확인 후 ACK하고, 기존 확정 기록이 확인된 재전달도 추가 차감 없이 ACK한다. DB 확인 불가 시 ACK를 보류한다. 실제 구현과 장애 주입 검증은 Phase 2에서 수행한다.

기간은 예약 시각 기준으로 판단한다. 종료 전에 유효하게 접수한 작업은 Worker가 종료 이후 읽어도 확정할 수 있어야 한다. 현재 `EventService.issue()`는 처리 시점의 기간을 검사하므로 그대로 재사용할 수 없다. 예약 이벤트의 출처·필드·기간을 검증하는 별도 확정 경로와 변경 불가능한 이벤트 설정을 설계해야 한다.

예약은 Redis 스크립트 실행 순서로 결정되며 HTTP 도착 순서에 대한 공정성을 보장하지 않는다. Worker의 최종 DB 확정 순서도 예약 순서와 같다고 보장하지 않는다. 성능 우위는 DB 방식과 같은 조건으로 측정한 후 판단한다.
