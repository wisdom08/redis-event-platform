# ADR 0004: DB 기반 쿠폰 발급 기준 구현

- 상태: Accepted
- 날짜: 2026-11-15

## 결정

Redis Lua와 비교할 기준 구현으로 MySQL 트랜잭션 기반 발급을 먼저 만든다. 비즈니스·영속화 코드는 modules/event, HTTP 계층과 Clock 설정은 apps/event-api에 둔다. 모듈 간 의존성은 추가하지 않는다.

데이터 접근은 Spring JDBC를 사용한다. 재고 변경 SQL과 행 잠금, 영향받은 행 수를 직접 확인하기 위한 선택이다. 현재 Entity는 없으며 JPA ddl-auto: validate 설정은 향후 Entity 매핑에 적용된다. Flyway만 스키마를 변경한다.

발급 트랜잭션은 READ COMMITTED로 다음 순서를 따른다.

1. 양수 이벤트/사용자 ID 검증.
2. events PK로 SELECT FOR UPDATE하여 이벤트 행 잠금.
3. 같은 이벤트·사용자 발급 여부 확인. 이미 확정됐다면 ALREADY_ISSUED.
4. 잠금 획득 이후 앱 Clock 기준으로 시작 <= 현재 < 종료 검증.
5. remaining_quantity > 0 조건으로 재고 1개 차감. 변경 행이 없으면 SOLD_OUT.
6. 확정 발급 INSERT 후 커밋. 저장 실패 시 재고 차감도 롤백.

동일 이벤트의 발급은 행 잠금으로 직렬화되며, DB UNIQUE는 최종 중복 방어선이다. 모든 발급 쓰기는 이 경로를 사용해야 재고와 기록이 일치한다. PK·FK·UNIQUE·NOT NULL은 DB에, 수량·기간·식별자 검증은 앱에 둔다. SQL의 재고 조건은 동시성 안전한 변경을 위한 조건이다.

## API 정책

이벤트 이름은 공백만 아닌 1~200자, 수량은 양수, 기간은 시작 < 종료다. 시간은 UTC Instant를 사용하고 DATETIME(6)에 맞춰 마이크로초로 절삭한 뒤 검증한다. 저장 범위는 UTC 1000~9999년이다.

재요청은 최초 발급 결과를 자동 반환하지 않고 409 ALREADY_ISSUED를 반환한다. 이는 요청 키 기반 멱등성 프로토콜과 구분한다. 기존 결과는 GET으로 조회한다. 중복 검사는 기간·품절보다 우선한다. 발급 이력 없는 사용자에 한해 기간·재고를 검사한다.

입력 오류는 400, 미존재 이벤트/발급은 404, 중복·기간·품절은 409다. 잠금 획득 실패·데드락은 503 RETRY_LATER와 Retry-After: 1로 응답하고 서버 자동 재시도는 하지 않는다. 응답 유실 등으로 확정 여부가 불명확하면 결과 조회를 우선한다.

## 보장 범위와 한계

잠금 획득 순서와 네트워크 요청 도착 순서는 다르므로 엄격한 선착순·공정성을 보장하지 않는다. 기간은 잠금 획득 후 검사 시점 기준이며 최종 커밋이 종료 전이라는 보장은 없다. 이벤트별 행이 병목일 수 있으나 성능 수치는 아직 측정하지 않았다.

HTTP userId는 학습용 입력이며 인증·권한 검증을 구현하지 않았다. Redis는 현재 readiness 연결 외 발급 경로에 참여하지 않는다. Streams·Worker·예약/발행 경계 및 Redis 장애 보장은 후속 범위다.
